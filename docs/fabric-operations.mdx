# PAIR Fabric operations

This is the deployment runbook for the distributed compute fabric. It covers
pairing, worker installation, portable bundles, health checks, and recovery.
The fabric is a logical inference service: it can route or explicitly execute
runtime work across trusted workers, but it cannot make Windows, Linux, CUDA, or
Metal expose one pooled OS CPU/GPU/VRAM device. CPU RAM is model storage or
offload memory, not VRAM.

## 1. Choose the coordinator

Run the PAIR desktop application on the Windows workstation. It supervises the
broker and fabric coordinator. Keep TCP `14321` reachable for cluster pairing
and TCP `14324` reachable only between paired fabric members. Do not expose raw
llama.cpp RPC ports (`50052`, `51001`, etc.) to the LAN or internet.

Workers may be Windows, Linux, macOS, WSL2, an AWS VM, a DGX, or a mini-PC.
Install the worker on each machine; install an engine/model only where that
machine has enough memory and a compatible backend.

## 1.1 View the fleet

The Windows Electron dashboard is the operator console. Open the normal PAIR
window and go to the Overview/node list. The **Distributed inference fabric**
card refreshes every five seconds and lists each worker's state, runtime,
backends, free host memory, heartbeat probe latency, checkpoint support, RPC
support, jobs, GPU count, free/total VRAM when NVIDIA telemetry is available,
and executions. RPC support is a live local-target probe and the gate for
llama.cpp distributed placement; GPU/CPU telemetry alone does not make a
worker eligible for a pooled runtime.
The regular node cards remain the engine/model view; the fabric
card is the compute-plane view. A worker showing `ready` means authenticated
and admitted for scheduling, not that a model is currently loaded.

For automation or diagnostics, query the authenticated coordinator endpoint:

```text
GET https://coordinator:15424/v1/fabric/status
```

The development smoke coordinator uses `15424`; a normal installation uses the
fabric service port `14324`. The UI hides this distinction through the broker.

### WSL2 RPC relay note

When llama.cpp runs inside WSL2 but the RPC worker is on another machine, bind
the Windows relay to an address reachable from WSL2, such as `0.0.0.0:51006`,
and connect to the Windows host address from WSL2. A relay bound only to
`127.0.0.1` is for Windows-local clients and is not reliably reachable from
WSL2. PAIR's coordinator-launched WSL path performs this automatically: it
discovers the WSL default-route gateway, allocates relay listeners from the
dedicated TCP range `52000-52999`, and gives the WSL child the gateway address.
The Windows installer opens that range only for the PAIR fabric executable and
only from the local subnet. Keep the relay on a trusted/private interface and
never expose the raw RPC service directly.

```powershell
nvpair-compute-fabric.exe --daemon `
  --cluster-dir C:\PAIR\cluster `
  --rpc-relay-listen 0.0.0.0:51006 `
  --rpc-relay-url https://<worker-address>:14324/v1/fabric/rpc `
  --rpc-relay-peer-id <paired-dgx-node-uuid>
```

```bash
llama-server -m /path/model.gguf --rpc <windows-host-ip>:51006 \
  --n-gpu-layers 99
```

The llama.cpp client and DGX `ggml-rpc-server` must be built from compatible
revisions with `GGML_RPC=ON`. Verify that the client reports an `RPC0` device,
the DGX log reports CUDA buffer allocation/graph execution, and the request
returns HTTP 200. A heartbeat or open TCP port alone is not inference proof.
For the current DGX GB10 validation, use the matched llama.cpp `b8487`
revision (`f93c09e26`) on both sides. PAIR-owned WSL and DGX RPC paths now use
this revision; the previous binaries are retained as `.pre-b8487` backups.
Other llama.cpp/SGLang/Ollama projects are outside PAIR's managed paths.
On Linux and WSL, the fabric supervisor automatically adds the selected
executable's directory to the dynamic-library search path, so a llama.cpp
build with adjacent `libggml*.so` files can be supervised without a wrapper.

## 2. Launch distributed inference from the dashboard

The **Distributed inference** card appears above the training card in the
Windows Electron node view. Enter a model path readable by the coordinator,
the model SHA-256 digest, the configured `llama-server` path, an HTTP port, and
the desired CUDA worker count. **Start distributed inference** asks the broker
to admit the workers, creates authenticated RPC relays, and launches one
llama.cpp HTTP service. The card shows the remote RPC peer count and refreshes
the job state. Optional slot-save and checkpoint fields enable periodic
checkpoint capture and verified slot restore after worker loss. Stop the job
from the same card.

Use **Preview admission** first to run the coordinator's real placement checks
without launching a process. The preview shows the selected worker IDs and
plan epoch; a failed preview explains why the requested group cannot currently
be formed.

Checkpoint filenames are relative slot names, not arbitrary filesystem paths;
llama.cpp rejects path separators. PAIR writes the configured checkpoint file
under the supplied `--slot-save-path` directory and sends the filename in the
JSON request body to `/slots/<slot>?action=save` or `restore`.

The execution line in the card is a live control-plane view. `starting` means
the supervised process is alive but `/health` has not answered yet;
`serving` means the HTTP health check succeeded; `recovering` means a worker
was removed and PAIR is selecting a replacement epoch. The line also shows
the selected workers, epoch, checkpoint stage, and bounded recovery count.
`failed` means the process or recovery path needs operator action; `stopped`
is intentional termination. The dashboard never displays model prompts or
response bodies in this status view.

The model path is local to the coordinator because llama.cpp streams the
selected tensors to RPC workers; workers do not need a second copy for this
inference path. Training has separate per-node path requirements.

The RPC connection is a live byte stream, not a REST request. A successful
heartbeat or `rpcSupport:true` means that the worker's local RPC port answered
a probe; it does not prove that a model can finish loading. The execution
manager now runs an accept loop for every dynamic relay, pins each relay's
client certificate to the selected worker identity, and stops automatic
inference recovery after three failed attempts. A failed load therefore
becomes a visible failed job instead of an unbounded restart chain.

The inference group is requested as `llama.cpp` and filtered by backend (such
as `cuda`). A worker may therefore advertise `runtime: cuda` while still being
eligible for a llama.cpp group; `runtime` describes the worker execution
capability and `backends` describes the concrete acceleration options.

Headless operators can use the coordinator's pinned-mTLS endpoints
`/v1/fabric/inference/start`, `/v1/fabric/inference/status`, and
`/v1/fabric/inference/stop`; they use the same planner and supervisor as the
Electron card. The start body is the same `FabricInferenceRequest` shape, and
`jobId` is a query parameter for status and stop.

When checkpointing through WSL, PAIR creates the configured Linux slot
directory with `wsl.exe ... mkdir -p` before launching the server. The path is
passed as a structured argument and is never evaluated through a shell.

### Windows coordinator with a WSL llama-server

If the CUDA-enabled `llama-server` exists only in WSL, enable **Run through
WSL** on the inference card. Set the WSL distribution and Linux executable
path, and enter the model path in WSL form (for example,
`/mnt/c/Users/you/models/model.gguf`). PAIR supervises `wsl.exe` as the child
process and still creates the authenticated RPC relays itself; no shell command
or manual tunnel is required.

## 3. Pair a device

In the desktop UI, open **Settings > Cluster** on the Windows coordinator and
choose the discovered device under **Available nodes to add**. If discovery is
disabled or crosses a routed network, add the device as a manual node with its
reachable address and port `14321`.

The inviting device displays a six-digit PIN. On the invited device, accept the
new invitation and enter that PIN. Confirm both devices show the other under
**Connected nodes**. The PIN is out-of-band and is never written to logs.

The protocol equivalent is:

1. The coordinator calls `cluster:invite-node` with the worker address, port,
   and optional node ID.
2. The coordinator displays the returned `pin`.
3. The worker receives `cluster:invite-received` and calls
   `cluster:respond-to-invite` with `accept:true` and the human-entered PIN.
4. Both sides wait for `state:"paired"`, then persist the reported cluster
   identity. Wrong PIN, decline, timeout, or an already-clustered node is a
   terminal result, not a successful pairing.

Pair each worker to the same cluster. Never copy a node's private key or an
existing cluster directory to another machine; identities must be generated on
the machine that owns them.

## 3. Install a portable worker

The release/source tree provides `package-fabric-windows.ps1`,
`package-fabric-linux.sh`, and `package-fabric-macos.sh`. Each archive contains
the fabric executable, an installer/launcher, this documentation, and a SHA256
manifest. Archives intentionally exclude certificates, private keys, cluster
state, SSH keys, and models.

When building macOS artifacts on Windows, use
`package-fabric-macos-cross.ps1` with a cross-compiled binary. It produces the
same worker-only archive and SHA256 manifest as the native macOS packager.

On Windows, `package-fabric-windows.ps1` uses the staged service binary by
default. To package a freshly built portable binary from another output
directory, pass it explicitly with `-Binary`.

```powershell
.\scripts\package-fabric-windows.ps1 -Binary .\desktop\cli-bin\nvpair-compute-fabric.exe
```

### Windows

Extract `fabric-windows-x64.zip`, set these values in a PowerShell session, and
run `run-fabric-worker.ps1`:

```powershell
$env:PAIR_COORDINATOR_URL='https://coordinator.example:14324'
$env:PAIR_WORKER_ID='win-worker-01'; $env:PAIR_NODE_ID='WIN-01'
$env:PAIR_CLUSTER_DIR='C:\Users\you\AppData\Local\PAIR\cluster'
.\run-fabric-worker.ps1
```

Use `install-fabric-worker-windows.ps1 -Task` to register a per-user logon
task. It needs no administrator rights. For a Windows GPU, set
`PAIR_RUNTIME=cuda` and use a CUDA-capable llama.cpp RPC build; otherwise use
`cpu`. The launcher passes `--daemon`, so it stays alive without broker stdin.

### Linux: DGX or mini-PC

Extract `fabric-linux-x64.zip`, provision the paired cluster directory, then:

```bash
export PAIR_FABRIC_BINARY="$PWD/nvpair-compute-fabric"
export PAIR_CLUSTER_DIR=/var/lib/nvpair/cluster
export PAIR_COORDINATOR_URL=https://coordinator.example:14324
export PAIR_WORKER_ID=dgx-01 PAIR_NODE_ID=DGX-01
export PAIR_RUNTIME=cuda PAIR_BACKEND=cuda
sudo -E ./install-fabric-worker.sh
sudo systemctl enable --now nvpair-fabric-worker
```

Use `PAIR_RUNTIME=cpu` and `PAIR_BACKEND=cpu` on CPU-only mini-PCs. Set
`PAIR_RUNTIME=cuda` only after `nvidia-smi` and a local CUDA llama.cpp build
work. The service restarts after a crash and re-enters the fabric through a
fresh authenticated heartbeat. If a CUDA llama.cpp build already exists, pass
its `ggml-rpc-server` through `PAIR_RPC_SERVER_PATH`; the installer supervises
that helper without changing the source project or its models.

### DGX preflight

Set the DGX address and SSH user for your environment. From the Windows
coordinator, validate access before attempting PAIR installation:

```powershell
ssh <dgx-user>@<dgx-address> "hostname; nvidia-smi; docker info"
Test-NetConnection <dgx-address> -Port 14321
Test-NetConnection <dgx-address> -Port 14324
```

SSH must use the key authorized on the DGX. Do not reuse the AWS key unless it
has explicitly been authorized there. After SSH works, copy/extract the Linux
bundle, create the DGX's local cluster identity by pairing it from **Settings >
Cluster**, and install it with `PAIR_RUNTIME=cuda` / `PAIR_BACKEND=cuda`. The
DGX should then appear as `ready` in `/v1/fabric/status` and pass a small
completion test before it is admitted to production jobs.

The desktop coordinator address and DGX worker address are installation-specific.
Use the authenticated status query in the verification section to confirm that
the worker is `ready`; the dashboard reads live coordinator state rather than a
hand-maintained status file.

### macOS

Extract `fabric-macos-arm64.zip` or the matching architecture archive, set the
same required `PAIR_*` values, and run `install-fabric-worker-macos.sh`. It
installs a per-user launchd agent with `RunAtLoad` and `KeepAlive`. Use
`PAIR_RUNTIME=metal` with a Metal-capable engine; capability detection alone
does not build or install Metal llama.cpp.

## 4. Verify a worker

The coordinator status endpoint is:

```text
GET https://coordinator/v1/fabric/status
```

The worker must be `ready`, have a recent heartbeat, and show the expected
runtime/backends. A ready heartbeat is not proof of inference. Send a small
OpenAI-compatible completion through the configured llama-server and verify a
generated response. Inspect service logs for `worker rejoined` after a restart;
never treat a stale status file as health evidence.

## 5. Failure and recovery

Missed heartbeats stop new work, then quarantine the worker. The coordinator
rebuilds a compatible group and resumes only from a valid checkpoint supported
by the selected runtime adapter. When the node returns, it completes a new
mTLS handshake and capability probe before rejoining the queue. A runtime that
cannot restore its checkpoint reports failure rather than replaying side
effects silently.

For distributed training, a refreshed rank failure becomes `recoverable`.
When the coordinator has ready same-backend replacement workers and a verified
checkpoint, it automatically launches a complete replacement world with a
new rendezvous epoch and `--resume`. If either condition is missing, the
dashboard keeps the group recoverable and requires an operator to provide the
replacement set. Recovery is capped at three attempts.

## 6. Security and fleet rules

Use a private network or a narrowly scoped firewall rule for `14321` and
`14324`. Pair before admitting compute work. Do not put `.pem`, `.key`, cluster
directories, PINs, model files, or SSH credentials into a bundle or repository.
For AWS smoke tests, a reverse SSH tunnel is acceptable for private testing;
production should use a controlled route and rotate access credentials normally.

For 50 mini-PCs, automate only after one CPU node has passed pairing, status,
completion, crash restart, and rejoin tests. Give every device a unique worker
ID, node ID, cluster identity generated locally, and a measured role (`cpu`,
`cuda`, or `metal`). Adding more machines increases aggregate throughput and
capacity; it does not create a zero-latency shared memory pool.
