# PAIR logical device architecture

PAIR can present a heterogeneous fleet as one logical inference or training
service, but there are three different meanings of “one device.” They must not
be conflated.

## What the operating system can see

Windows, CUDA, and Metal enumerate device objects owned by a local driver and
address space. A network worker cannot be added to an existing NVIDIA CUDA
device by changing an environment variable. A true OS-visible adapter would
require a signed WDDM kernel-mode miniport and matching user-mode driver, plus
a protocol that implements allocation, command submission, synchronization,
residency, reset, and fault handling. WDDM’s GPU paravirtualization model is
designed around a tailored guest driver and a host GPU-PV implementation; it is
not a generic bridge for arbitrary remote GPUs.

NVIDIA vGPU can expose multiple virtual GPUs to a VM, and multi-vGPU can use
multiple vGPU resources in supported environments, but it remains a
hypervisor/vendor feature with hardware, product, licensing, and topology
constraints. It does not combine this Windows PC, a Mac Metal device, an AWS
CPU, and a DGX GB10 into one CUDA device.

Metal likewise creates a `MTLDevice` for each local GPU. Metal resources are
owned by their device and cannot be passed to a different device as if it were
the same address space.

## What is technically available below the OS-device boundary

CUDA VMM and fabric memory can map allocations across supported NVIDIA
multi-node NVLink fabrics. NVSHMEM exposes a partitioned global address space
for supported NVIDIA GPU clusters. Those mechanisms still require participating
CUDA processes and supported interconnects; they do not make Ethernet-attached
or Metal devices appear in `cudaGetDeviceCount()`.

This is the strongest “shared memory” direction for a homogeneous NVLink
cluster. It is not a solution for the current RTX 5060 + DGX + Mac + mini-PC
fleet, because those nodes do not share one CUDA fabric and do not share one
driver address space.

## PAIR’s novel practical route: a logical tensor device

PAIR should expose a device-neutral logical tensor runtime above the local
drivers:

1. The coordinator creates a versioned logical device plan with tensor shards,
   memory tiers, placement, transport, and failure policy.
2. Each worker owns local CUDA, Metal, or CPU allocations. No remote pointer is
   fabricated and no invalid CUDA pointer is handed to an application.
3. The runtime moves explicit tensor pages or collective buffers between
   workers. Hot weights remain local; cold weights and KV-cache pages may live
   in host RAM or on another worker.
4. Pipeline and tensor-parallel stages overlap compute and transfer. A page
   fault becomes an asynchronous fabric fetch with admission control and
   bounded retry, not a blocking illusion of zero-latency shared memory.
5. Every stage boundary has a checkpoint and epoch. A failed worker is removed,
   a replacement plan is created, and only verified state is resumed.

This gives applications a single PAIR endpoint and a model larger than one
local GPU, while preserving the performance and correctness boundary that the
OS and local GPU APIs require. It can support heterogeneous CPU/CUDA/Metal
workers through explicit adapters; it cannot honestly promise one pooled VRAM
device to arbitrary existing CUDA or Metal applications.

## Current implementation boundary

The fabric implements worker capability discovery, authenticated RPC-relay
execution, replicated/tensor/pipeline plan metadata, distributed training
checkpoints, bounded training recovery, and the first logical-device control
plane. The coordinator now exposes logical-device capability description,
planning, status, page-transfer admission, and degraded-plan recovery through
the `fabric:logical-device-*` methods. Plans carry explicit page owners,
memory tiers, request IDs, and epochs; a transfer remains queued until a
matching digest is reported, and recovery creates a newer epoch on ready
replacement workers.

The provider acknowledgment method is
`fabric:logical-device-transfer-complete`; it accepts only a transfer ID and
destination digest. The coordinator publishes the destination as owner only
after that digest matches the admitted transfer.

The binary data path is the existing worker mTLS listener at
`/v1/fabric/logical-page`. It streams page bytes with explicit size and digest
headers into a bounded, atomic local page store. This is a PAIR data channel,
not shared CUDA address space; CUDA/Metal adapters may optimize local copies,
but ownership is published only after peer metadata verifies the bytes.

Provider-level tensor execution and the binary data channel are still the next
runtime phase. Until those are implemented and benchmarked, a queued transfer
is control-plane state rather than proof that tensor bytes moved, and aggregate
capacity in the dashboard means schedulable fleet capacity, not a contiguous
memory pool.
