# Distributed Compute Fabric

The distributed fabric is PAIR's explicit compute plane for making several
trusted machines act as one logical inference runtime.

## Recommended topology

Use the Windows workstation as the operator and coordinator first:

```text
Windows PAIR coordinator
    ├── DGX CUDA worker
    ├── RTX 5060 CUDA worker
    ├── MacBook Pro Metal worker
    └── CPU/RAM workers
```

The coordinator does not turn these devices into one operating-system GPU. A
distributed runtime must explicitly place model layers or tensor work and send
activations between workers.

The coordinator can convert an admitted group into a versioned execution plan
with `fabric:build-execution-plan`. The plan records the model digest, runtime,
replicated/tensor/pipeline shard strategy, authenticated transport, worker shard
assignments, per-worker host/GPU memory budgets, checkpoint interval, and bounded
failover policy. Aggregate dashboard capacity alone never authorizes a job.

## Distributed training

PAIR also defines a training-adapter boundary. `fabric:build-training-command`
generates a `torchrun` command with a c10d rendezvous, stable job identity,
node rank, FSDP or data-parallel mode, model digest, dataset, and checkpoint
arguments. The current adapter requires homogeneous CPU or CUDA workers. It
does not pretend that a Mac Metal worker can join a CUDA collective, and it
does not turn CPU RAM into VRAM. A future adapter can provide Metal-capable
collectives or another runtime behind the same plan contract.

Worker nodes expose authenticated training lifecycle endpoints for start,
status, and stop. The coordinator must send the same validated request and
node rank to each assigned worker; each worker launches its local `torchrun`
without a shell, allowing the collective runtime to establish its rendezvous.
This is a real process-supervision path, but a trainer script and compatible
PyTorch environment must still be installed on every participating node.

The coordinator method `fabric:training-start` performs this fan-out across the
assigned nodes and rolls back partial launches. Later recovery can reuse the
same request with a new rendezvous and the last verified checkpoint.

The paired `fabric:training-status` and `fabric:training-stop` methods expose
rank-level state and stop the complete world, preventing an orphaned rank from
continuing after an operator cancellation. Status refresh queries every
assigned worker over pinned mTLS before returning the dashboard view; a failed
rank changes a running group to `recoverable` so the recovery action is based
on observed worker state rather than a stale launch record.

`fabric:training-recover` accepts replacement workers and a fresh rendezvous,
restores the last verified checkpoint through the trainer's `--resume` contract,
and bounds recovery to three attempts. A failed recovery remains visible as
`failed`.

`fabric:training-checkpoint` persists a monotonic checkpoint manifest tied to
the group epoch. Coordinator restart changes an old `running` group to
`recoverable`; it does not claim that the old OS processes survived. Recovery
must use that verified checkpoint and a fresh rendezvous.

## Worker states

Workers move through `discovered`, `authenticated`, `probing`, `ready`,
`leased`, `serving`, `suspect`, and `quarantined`. Missed heartbeats stop new
assignments before quarantine. A worker that returns must complete a fresh
mutual-TLS handshake and capability probe; stale worker epochs cannot resume an
old job.

## Device groups

CPU, CUDA, and Metal are separate capabilities. Homogeneous groups are the
default. Mixed groups require an explicit compatibility probe and measured
latency/bandwidth check. A DGX and RTX 5060 may be faster as separate request
targets than as a single distributed model group, depending on the model and
network.

## Failure and recovery

Distributed jobs carry a group ID, model digest, epoch, and checkpoint stage.
When a worker fails, the coordinator quarantines it, rebuilds a compatible group,
and resumes only from a valid checkpoint supported by the runtime adapter. A
runtime that cannot restore a stage reports failure rather than silently replaying
tokens or side effects.

## Current implementation status

Hardware capability reporting is implemented. Existing Ollama and LM Studio
routing is unchanged. The coordinator is broker-supervised, packaged as
`nvpair-compute-fabric`, and exposes the cluster-mTLS `cf` service on TCP
`14324`. Worker mode sends authenticated heartbeats and performs a fresh epoch
rejoin after quarantine. Its llama.cpp adapter can supervise a loopback
`ggml-rpc-server`, create authenticated RPC relays, and launch a local
OpenAI-compatible `llama-server` using those relays.

NVIDIA workers also report aggregate GPU count and free/total VRAM in each
heartbeat when `nvidia-smi` is available. The dashboard displays this beside
host-memory capacity. A device that is visible but does not expose memory
accounting is still counted as GPU-capable with unknown VRAM. Unknown VRAM
never satisfies a minimum-VRAM admission constraint, preventing optimistic
placement on platforms such as DGX GB10.

Do not expose a raw distributed-runtime port to the LAN. Only the PAIR
cluster-mTLS endpoint should be reachable, and only after the participating
machines have been paired.
The coordinator now performs capability-aware ready-worker group planning and
persists job checkpoints by epoch. For llama.cpp, slot checkpoints can be saved and restored through the server slot API when `--slot-save-path` is configured. A failed group can therefore be replaced by
a new group and resumed from the last accepted stage when the runtime adapter
supports that stage. Group planning is not tensor execution: it will reject
unsupported or under-capacity groups rather than silently mixing devices.

GPU-aware placement can additionally set `minGpuVramTotalBytes` and
`minGpuVramFreeBytes`. Workers without reported NVIDIA VRAM do not satisfy
those constraints, preventing assignment to a worker that cannot prove enough
GPU capacity.

The coordinator JSON-RPC surface includes `fabric:job-start`, `fabric:job-stop`, and `fabric:job-status`; job start derives authenticated loopback relays from worker heartbeat endpoints and launches the configured llama.cpp server. The worker must advertise its fabric HTTPS endpoint with `--advertise-url`.

`fabric:get-status` also returns a `capacity` object. Its values are the sum of
currently `ready` workers’ free host memory, reported GPU count, and reported
free/total NVIDIA VRAM. This is PAIR’s logical capacity view for scheduling;
it is not an OS-level unified memory device.

The desktop launcher accepts explicit adapter configuration through
`NVPAIR_FABRIC_*` environment variables (for example
`NVPAIR_FABRIC_LLAMA_SERVER_PATH`, `NVPAIR_FABRIC_LLAMA_MODEL`,
`NVPAIR_FABRIC_LLAMA_RPC`, and `NVPAIR_FABRIC_RPC_RELAY_SPECS`). This keeps distributed execution opt-in while
allowing the Windows coordinator to be operated from the normal Electron UI.

## Verified Windows and WSL path

The first end-to-end smoke path is Windows as coordinator plus Ubuntu WSL2 as a CPU worker. The worker runs `nvpair-compute-fabric`, supervises `ggml-rpc-server`, and the local `llama-server` connects to the coordinator's authenticated relay. The status endpoint is:

```text
GET https://<coordinator>/v1/fabric/status
```

The response must show the worker as `ready` and include a recent heartbeat. Inference must also be tested through the worker's OpenAI-compatible server; an accepted heartbeat alone does not prove model execution.

WSL2 can see the Windows NVIDIA device through `/usr/lib/wsl/lib/nvidia-smi`. For an RTX 5060, use a CUDA toolkit that supports compute capability 12.0 (CUDA 12.8 or newer). CUDA 12.0 cannot compile `compute_120`, so a CPU worker is the correct fallback until the newer toolkit and CUDA llama.cpp build are available. NVIDIA's WSL guidance says to install the toolkit package only and not a Linux driver inside WSL.

## Fleet worker installation

For Linux mini-PCs, use scripts/install-fabric-worker.sh after the node has been paired and its cluster directory has been provisioned. It installs the worker as a systemd service with automatic process restart and passes `--daemon`, so it is not dependent on a broker JSON-RPC stdin session. The installer defaults to a 10-second heartbeat timeout for higher-latency links; override `PAIR_HEARTBEAT_TIMEOUT` when appropriate. Set PAIR_RUNTIME=cpu and PAIR_BACKEND=cpu for CPU-only machines; use PAIR_RUNTIME=cuda only after a local CUDA probe succeeds. For a node that should supervise llama.cpp, set `PAIR_RPC_SERVER_PATH` for `ggml-rpc-server`; set `PAIR_LLAMA_SERVER_PATH`, `PAIR_LLAMA_MODEL`, and `PAIR_LLAMA_PORT` for a local compatible `llama-server`. `PAIR_LLAMA_RPC` is optional for static RPC targets; coordinator-launched jobs create authenticated relays dynamically. The installer accepts an optional PAIR_FABRIC_SHA256 and never accepts or writes a private SSH key.

For a MacBook Pro, use scripts/install-fabric-worker-macos.sh after pairing. It installs a per-user launchd agent with `KeepAlive`, defaults to `PAIR_RUNTIME=metal` and `PAIR_BACKEND=metal,cpu`, and uses the same `--daemon` worker protocol. Set `PAIR_RPC_SERVER_PATH` to a Metal-capable `ggml-rpc-server` build when the node is used for llama.cpp RPC execution; capability detection alone does not guarantee that an engine build supports Metal.

## AWS and other remote nodes

An AWS Ubuntu instance or a CPU-only mini-PC can join as a CPU worker. It needs the Linux `nvpair-compute-fabric` binary, a paired cluster identity, and TCP `14324` reachability to the Windows coordinator. A reverse SSH tunnel is useful for a private smoke test; production enrollment should use a narrowly scoped firewall rule and mutual TLS. Do not copy the private key used to reach an AWS instance into the repository or a node bundle.

## What “one machine” means here

The fabric can expose one logical inference service by explicitly routing requests, model stages, or runtime RPC work. It cannot make Windows Task Manager, CUDA, DirectML, or Metal report one pooled CPU/GPU/VRAM device. CPU RAM can be used as a model offload/cache tier, but it is not GPU VRAM and usually adds latency. Workers now advertise `rpcSupport` separately from CPU/GPU telemetry; the worker sets it only when its local RPC target answers a TCP probe, and mixed CPU/CUDA llama.cpp groups are admitted only when every selected worker has that capability. The scheduler therefore keeps hardware capabilities distinct, measures the network, and only forms a group when the selected runtime adapter supports that execution mode.

### Current live test evidence

The Windows↔WSL RTX 5060 path has passed authenticated heartbeat, CUDA model load, and generated completion through the fabric relay. The AWS Ubuntu node has passed paired mTLS enrollment, fresh CPU heartbeats, and an end-to-end completion through the authenticated HTTPS CONNECT relay. A matched llama.cpp b8487 runtime is now installed in the PAIR-owned RPC paths on WSL and DGX, with the prior binaries retained as `.pre-b8487` backups. A fresh production-path canary loaded a 0.5B GGUF across the RTX 5060 and DGX GB10: the client reported both `RPC0` and local `CUDA0` devices, the DGX RPC process allocated remote model/compute buffers, and an HTTP completion returned generated text. This validates heterogeneous cross-machine model placement at the llama.cpp RPC layer. The AWS CPU worker now passes the live RPC-target probe and can be admitted to a mixed group, but an isolated AWS CPU llama.cpp canary did not reach `/health` or produce a completion; the AWS RPC binary still needs a matched b8487-compatible rebuild/probe before CPU participation is called production-ready. The previously installed newer revision reproduced `Remote RPC server crashed or returned malformed response`; it remains preserved only in the backups. Existing DGX projects were not changed. The smoke test uses private tunnels only to reach otherwise-private nodes; production deployment should use controlled network routes.
The live resilience gate has also passed for the DGX PAIR service: after a controlled service stop, the coordinator marked `dgx-spark-gb10` quarantined and reduced capacity to two workers/one GPU; after the service restart, a fresh epoch rejoined it as `ready` and restored three workers/two GPUs. This proves worker quarantine and automatic re-admission. A separate coordinator-launched WSL llama.cpp canary persisted a slot checkpoint, then recovered after its supervised `wsl.exe` child was terminated: the replacement process received a new PID, restored the checkpoint path, reconnected two RPC peers, and served another completion. This proves controlled checkpoint-aware child restart; it does not claim an in-flight token stream is transparently resumable.

The WSL launcher now resolves the WSL host gateway before starting a grouped
llama.cpp server. Dynamic relays bind on `0.0.0.0` only for that child path,
allocate from PAIR's reserved `52000-52999` TCP range, and advertise the
gateway address, so the Linux process can reach a Windows relay. The Windows
installer adds a local-subnet firewall rule for that executable and range.
Every relay carries the selected worker's pinned node identity. Recovery is
bounded to three attempts and then records the job as failed. A raw SSH
comparison against the AWS CPU RPC daemon loaded the test model on both
`RPC0` (AWS) and `CUDA0` (RTX 5060), confirming that the AWS daemon and network
transport are usable. The PAIR HTTPS relay can establish its authenticated
CONNECT stream and reach the daemon, but the AWS CPU grouped canary did not
finish model initialization within the validation window; AWS CPU execution
remains an integration item rather than a production-ready claim.

## Execution observability

Every coordinator-launched inference execution exposes a lifecycle record to
the dashboard and the pinned status endpoint. It identifies the phase
(`starting`, `serving`, `recovering`, `failed`, or `stopped`), selected worker
IDs, plan epoch, recovery attempts, checkpoint progress, and the last update
time. `serving` is only reported after the supervised llama.cpp HTTP health
endpoint responds successfully; WSL probes run inside the selected
distribution without shell evaluation. This is control-plane evidence of
readiness and placement, not a claim that an in-flight token stream can be
transparently migrated between machines.

When more than one peer is pinned, configure a relay with the exact destination identity using `--rpc-relay-peer-id <node-uuid>`. This prevents a relay from presenting an arbitrary local cluster certificate to a heterogeneous peer.
